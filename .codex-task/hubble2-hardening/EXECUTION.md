# Hubble 2.0 Hardening Execution Rules

> 本文件只定义执行方式，不记录当前完成状态。当前状态与 blocker 仅以 [`TODOs.md`](TODOs.md) 为准；
> 稳定产品/API 决策写入 accepted design；命令、版本、日志和截图等运行事实写入日期 evidence。

## 1. 验证分层

按以下三层执行，禁止每个微小改动都立即重复完整发布包构建：

1. 单项 RED/GREEN：只运行受影响的 Jest/Java test、scoped ESLint 和必要 i18n 检查。
2. 环境批次门禁：同一环境的一批 findings 修复冻结后，统一运行完整 Jest、全 JS ESLint、i18n、
   `CI=true` production build、受影响 Java/Client/Loader 检查。
3. 发布包验收：批次门禁通过后只构建一次真实 Hubble 发布包，并用该包完成真实服务和 Chrome 复验。

完整 build/package 默认只在以下里程碑运行：

- non-PD 修复批次冻结；
- PD 修复批次冻结；
- 最终 diff 冻结、提交或远程检查前；
- reviewer actionable findings 修复后的最终复验。

如果改动直接影响 assembly、静态资源装配、启动脚本或发布包内容，可提前运行对应发布包检查，但需在
evidence 说明原因。

本地 Maven 命令默认使用已验证的 Java 11 `mvnd` daemon 复用 JVM、依赖图和后台服务；定向测试、模块
install 与 package 均显式固定同一 `JAVA_HOME`。只有 `mvnd` 不可用、daemon 异常或待复现问题可能由
daemon 状态引起时才回退 `mvn`，并在 evidence 记录原因；远程 CI 仍使用仓库定义的原生命令，不以本地
daemon 改写门禁语义。

同一实施阶段固定使用同一个 `JAVA_HOME`、`mvnd` 可执行文件和仓库目录，不传 `--no-daemon`，也不在
相邻测试间主动执行 `mvnd --stop`；测试、compile、install、package 尽量连续交给同一 daemon。开始新
批次时可用 `mvnd --status` 核实复用状态，但 daemon 因空闲超时或异常退出时直接由下一条 `mvnd` 命令
重建，不能把 daemon 存活本身当成测试通过或服务就绪证据。

### 1.1 微小问题批处理

对于影响范围清楚、难度低、相互独立或属于同一页面/模块/数据链路的零碎问题，默认先聚合成一个可审查
批次再统一修复和确认，避免“修一个小点、跑一次完整测试、再修下一个小点”的串行循环：

1. 先完成同批 findings 的只读盘点、分级、文件所有权和共同验收矩阵；新发现仍需先登记 TODO。
2. 批量实现时保持每项改动最小、可定位，并为同批关键行为补足针对性测试；无需在每个微小提交后重复
   完整 Jest、production build、package 或 Chrome 全矩阵。
3. 同批实现冻结后，统一运行受影响测试和 scoped lint/i18n；全部通过后再执行一次环境批次门禁、一次
   发布包构建和一次真实 Chrome 矩阵验收。
4. 同一根因影响多个调用点时，应先确认统一 owner/契约，再集中修复所有已知调用点，避免只修首个症状。
5. 若某项出现高风险数据迁移、安全/认证边界、难以定位的回归、破坏性 mutation 或明显扩大影响范围，
   将其从微小批次拆出，单独执行 RED/GREEN 和风险相称的验证。

批处理提高执行效率，但不降低单项完成证据：批次验收记录仍需能够映射回每个 TODO、失败场景和实际
Chrome/后端状态。

默认验证单位是一个边界清晰、可整体回滚的小批次，而不是单个低风险 finding。批次大小以一次失败后能
快速定位到具体文件、调用点或测试为上限，不机械规定条目数；能共享同一测试命令、页面矩阵或发布包的
小修应优先合并验证。批次实施期间除以下情况外不逐项启动测试：

- 修改了同批其他修复依赖的公共契约、基础组件或测试 fixture，需要先确认基础仍可用；
- 首个针对性验证失败，需要立即缩小范围并二分定位；
- 改动风险在实施中升级，不再满足“影响清楚、难度低、可独立回滚”的批处理条件。

因此常规节奏应为“盘点并登记一批 → 集中修复 → 一次针对性测试/lint/i18n → 必要修正 → 里程碑统一
全量门禁与 Chrome 验收”，不得为了形式上的即时反馈让同一套慢测试在相邻小修之间反复运行。

## 2. 并行 lane

预计超过 30 秒的 build、package、CI、下载或服务等待期间，若存在不冲突工作，至少启动一个独立 lane：

- PD/HStore 配置和运行目录准备；
- 后端 CI/check 状态与日志收集；
- TODO/evidence 回填和证据结构化；
- 硬编码中文、路由、错误 owner、性能 warning 等只读审计；
- 下一环境 Chrome matrix/fixture 设计；
- 与当前修改文件不重叠的实现任务。

共享工作树的并行实现必须按文件或模块划分所有权；禁止两个实现者同时修改同一文件。最终 reviewer 必须
是未参与实现的独立只读 agent，不能用并行实现者替代。

## 3. 失败与重试

- 针对性测试先证明 RED，再实现并证明 GREEN；不得用 pipe、忽略退出码或截断输出推断成功。
- 网络、服务启动、Chrome 或 CI 暂时失败采用有限重试与退避；重试前先保存失败日志和根因线索。
- 服务必须以前台持久会话或已验证的后台机制运行，不能把随命令会话退出的 daemon 当成稳定环境。
- 只有真实双模式环境长期无法建立时才暂停询问用户；其他失败记录后继续可执行 lane。

## 4. Chrome 与发布包

- 页面、交互、路由、渲染、报错和英文体验的完成证据必须来自用户 Chrome 操作真实发布包页面。
- 单元测试、mock、源码开发服务器和 CI Playwright 不能替代 Chrome 证据。
- 同一批 UI 修复应在源码层集中完成，再统一重建发布包并一次性复验整批 finding。
- destructive mutation 仅使用隔离 fixture，并用 Server/PD 真实状态复核，不能只看 toast。

## 5. 状态与证据职责

- `TODOs.md`：只维护 checkbox、优先级、当前状态、blocker 与完成证据链接。
- `EXECUTION.md`：只维护执行规范，不记录某次运行是否完成。
- accepted design：稳定产品/API 决策与外部能力边界。
- `evidence/YYYY-MM-DD-*.md` 及附件：版本/SHA、配置、命令、退出码、CI URL、日志、JSON、截图。

新发现必须先在 TODO 分级；完成时回填日期、环境、版本/SHA 和 evidence 链接。不得以 execution 文档中的
原则性描述代替完成证据。
